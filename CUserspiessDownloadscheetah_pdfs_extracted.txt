ℹ   LTV  =  ARPU  (ARR  moyen  par  client)  /  Taux  de  churn  annuel Exemple  :  ARPU  =  6  000  EUR/an,  Churn  =  10%/an  →  LTV  =  60  000  EUR Payback  Period  =  CAC  /  (ARPU  mensuel  *  Gross  Margin  %) Exemple  :  CAC  =  3  000  EUR,  ARPU  mensuel  =  500  EUR,  GM  =  70%  →  Payback  =  3000  /  (500*0.70)  =  8.6  mois

2.5  NRR  —  Net  Revenue  Retention  
ℹ   NRR  =  (MRR  debut  de  periode  -  Churn  -  Contractions  +  Expansions)  /  MRR  debut  de  periode  *  100 NRR  =  100%  :  vous  remplacez  exactement  ce  que  vous  perdez.  Neutre. NRR  >  100%  :  vos  clients  existants  vous  rapportent  de  plus  en  plus.  C'est  le  Graal  —  la  croissance  organique  pure. NRR  <  100%  :  vous  perdez  du  revenu  sur  votre  base  existante.  Même  avec  de  l'acquisition,  vous  coulez  plus  vite. Standard  top-tier  (Datadog,  Snowflake,  Stripe)  :  NRR  >  130%.

3.1  Ce  que  Cheetah  ne  fera  JAMAIS  
Les  contraintes  négatives  sont  aussi  importantes  que  les  ambitions  positives.  Elles  empêchent  le  feature

POLICY   ·   Hard  Constraints  —  Cheetah  Never  List 1.  JAMAIS  un  module  de  gestion  de  projet  general  (Asana,  Monday,  Notion  replacement)  —  hors  périmètre. 2.  JAMAIS  une  fonctionnalité  qui  nécessite  >  3  clics  pour  une  action  quotidienne  des  utilisateurs. 3.  Jamais  du  code  propriétaire  sur  les  formats  de  données  —  toujours  export  standard  (CSV,  Excel,  JSON). 4.  JAMAIS  une  fonctionnalité  non  mesurable.  Pas  de  métrique,  pas  de  feature. 5.  JAMAIS  une  IA  générative  sur  les  données  financières  confidentielles  sans  consentement  explicite. 6.  JAMAIS  une  UI  qui  cache  les  chiffres.  Cheetah  est  datafirst  —  les  métriques  sont  toujours  visibles. 7.  Jamais  de  lock-in  propriétaire.  Les  clients  peuvent  exporter  100%  de  leurs  données  à  tout  moment. 8.  JAMAIS  une  fonctionnalité  de  reporting  'statique'  —  tout  rapport  est  recalculé  en  temps  réel.

A2.  Break-Glass  Procedures

A2.1  Principe  general  des  break-glass  
ℹ   Definition  :  Break-Glass  Procedure Littéralement  :  'casser  la  vitre'  —  la  procédure  d'urgence  réservée  au  moment  où  les  règles  normales  bloquent  une  action  critique. 5  éléments  obligatoires  :  (1)  trigger  documente,  (2)  chaîne  d'approbation,  (3)  audit  trail  immutable,  (4)  expiration  automatique,  (5)  post-incident  review  obligatoire  dans  les  72h. Une  procédure  break-glass  utilisée  plus  de  3  fois  en  30  jours  signale  un  problème  structurel,  pas  une  exception. 
 
A2.2  Procédure  BG-01  :  Hotfix  Production  en  urgence  
POLICY   ·   BG-01  —  Production  Hotfix  Bypass TRIGGER  :  incident  P0  actif  depuis  >  30  min  sans  rollback  possible  (ex  :  breaking  change  DB). APPROBATION  (chaîne  OU)  :  RECTO  seul,  OU  2  Tech  Leads  en  accord,  ou  CEO  +  1  Tech  Lead. AUDIT  :  commit  signe  avec  tag  'BREAK-GLASS-BG01'  +  lien  vers  ticket  incident. EXPIRATION  :  la  branche  hotfix  a  un  TTL  de  24h.  Après  :  merge  sur  main  +  revue  par  toute  l'équipe. POST-REVIEW  :  RCA  obligatoire  dans  les  72h  +  ajout  au  registre  des  dérogations. LIMITE  :  si  BG-01  utilise  >  2  fois  en  30  jours,  freeze  des  features  et  revue  CTO. 
 
A2.3  Procédure  BG-02  :  Acces  direct  base  de  production  
POLICY   ·   BG-02  —  Production  Database  Direct  Access TRIGGER  :  incident  nécessitant  inspection  ou  correction  manuelle  de  données  client  (P0/P1  uniquement). APPROBATION  (chaîne  ET)  :  CTO  +  ticket  incident  actif  +  tenant_id  spécifique  vise. AUDIT  :  session  enregistrée  (script  ou  outil  type  Teleport).  Toutes  les  requêtes  loggers. EXPIRATION  :  token  d'accès  TTL  1h  max.  Renouvellement  =  nouvelle  approbation. POST-REVIEW  :  log  analyse  par  RSSI  dans  les  24h.  Notification  tenant  si  donnees  lues. INTERDICTION  ABSOLUE  :  pas  d'acces  aux  donnees  T1  d'autres  tenants  pendant  la  session.

1.3  Les  3  erreurs  de  gouvernance  à  éviter  absolument  
▶   Erreur  1  —  Trop  de  réunions,  aucune  décision Symptôme  :  des  réunions  interminables  se  terminent  par  'on  se  repose  la  question  la  semaine  prochaine'. Solution  :  chaque  réunion  doit  produire  AU  MOINS  1  décision  actée,  datée,  et  documentée  dans  le  Decision  Log. 
 
▶   Erreur  2  —  Le  consensus  éternel  (la  paralysie  collégiale) Symptôme  :  on  attend  que  tout  le  monde  soit  d'accord  avant  d'avancer.  Résultat  :  on  n'avance  jamais. Solution  :  le  'Accountable'  a  le  droit  et  le  devoir  de  trancher  en  dernier  ressort,  après  consultation. 
 
▶   Erreur  3  —  Les  décisions  orales  qui  disparaissent Symptôme  :  'On  en  avait  parlé...  mais  personne  ne  se  souvient  de  ce  qui  avait  été  décidé.' Solution  :  toute  Décision  Record  (DR)  doit  être  documentée,  datée,  signée,  et  stockée  dans  un  outil  centralisé  (Notion,  Confluence).

2.1  Le  Bus  Factor  :  la  fragilité  cachée  
✔   Concrètement  :  Le  Bus  Factor Le  'Bus  Factor'  répond  à  une  question  cruelle  mais  indispensable  :  'Si  cette  personne  se  faisait  renverser  par  un  bus  demain  matin,  l'entreprise  pourrait-elle  continuer  à  fonctionner  ?' Bus  Factor  =  1  :  UNE  SEULE  personne  connait  ce  processus  ou  ce  système.  Si  elle  part  du  jour  au  lendemain,  tout  s'arrête. Bus  Factor  =  2  ou  plus  :  deux  personnes  peuvent  assurer  la  continuité.  C'est  le  minimum  acceptable  pour  tout  processus  critique. Chez  les  startups  SaaS,  le  Bus  Factor  moyen  est  de  1.3  —  ce  qui  signifie  que  la  plupart  des  entreprises  ont  un  Bus  Factor  de  1  sur  leurs  processus  les  plus  critiques.

3.4  Protection  par  la  vitesse  :  l'avantage  de  l'itération  
ℹ   Principe  :  Le  produit  le  plus  copiable  est  celui  qui  n'évolue  pas Si  Cheetah  sort  2  nouvelles  fonctionnalités  majeures  par  mois,  un  concurrent  mettrait  6  mois  à  copier...  ce  que  Cheetah  avait  il  y  a  6  mois. La  vitesse  d'itération  est  en  elle-même  un  mot.  Amazon  appelle  ça  'la  vitesse  comme  défense'. Combiné  avec  les  données  exclusives  et  les  coûts  de  changement,  c'est  une  triple  protection  pratiquement  infranchissable.

5.1  Zero  Trust  :  'Ne  faire  confiance  à  personne  par  défaut'  
✔   Concrètement  :  Le  modèle  Zero  Trust  renverse  complètement  la  logique  de  la  sécurité  classique Avant  (périmètre  de  sécurité)  :  le  réseau  internet  est  sûr,  l'extérieur  est  dangereux.  C'est  comme  un  château  fort  :  bien  protégé  à  l'extérieur,  totalement  libre  à  l'intérieur. Problème  :  si  un  attaquant  entre  (un  employé  piraté,  un  ordinateur  volé),  il  a  accès  à  TOUT. Zero  Trust  :  Personne  n'est  digne  de  confiance  par  défaut  —  ni  un  employé  au  bureau,  ni  un  appareil  de  l'entreprise,  ni  même  un  serveur  interne. 7.3  L'excitabilité  score  :  évaluer  chaque  fournisseur

8.3  Le  Runbook  :  le  manuel  de  survie  opérationnel  
ℹ   Définition  :  Un  Runbook  est  un  guide  étape  par  étape  pour  réagir  à  une  situation  d'incident  précise Exemple  :  'Si  l'alerte  DATA_CONNECTION_TIMEOUT  se  déclenche  à  3h  du  matin,  voici  exactement  les  7  étapes  à  suivre  dans  l'ordre.' L'objectif  :  n'importe  quelle  personne  autorisée  (même  en  pleine  nuit,  même  stressée)  peut  suivre  le  runbook  et  résoudre  l'incident. Un  bon  runbook  remplace  5  ans  d'expérience  par  15  minutes  de  lecture  et  d'exécution. 
 
Structure  obligatoire  d'un  Runbook  •   Titre  et  identifiant  :  Nom  de  l'incident  type  +  code  unique •   Détecté  par  :  Quelle  alerte  specifique,  quel  symptôme  observable •   Impact  potentiel  :  Qui  est  concerné,  quelle  fonctionnalité,  quelle  sévérité •   Etapes  de  diagnostic  (dans  l'ordre)  :  Questions  à  se  poser,  commandes  à  exécuter •   Étapes  de  résolution  (dans  l'ordre)  :  Actions  précises  avec  commandes  si  applicable •   Escalade  :  A  qui  appeler  si  le  problème  n'est  pas  résolu  en  X  minutes •   Post-incident  :  Que  remplir  dans  le  post-mortem,  que  noter  dans  les  logs  
8.4  Le  post-mortem  'sans  blâme'  :  apprendre  sans  punir  
Après  chaque  incident  P0  ou  P1,  une  rétrospective  formelle  doit  être  réalisée  dans  les  48  heures.  La
